# 设计文档：语义驱动的图谱知识查询系统

**涵盖版本**: v3.5（导入管线）→ v3.6（语义元数据）→ v3.7（GraphRAG 6层管道）→ v3.8（查询性能优化）  
**目标**: 将查询系统从硬编码医疗领域改造为语义驱动的多系统通用查询引擎；引入关系语义元数据配置体系；构建缓存分层 + Few-shot 增强的 GraphRAG 管道。

**版本脉络**:
- **v3.5**: 导入管线（检测→验证→生成→回滚）
- **v3.6**: 关系语义元数据 + 语义驱动查询
- **v3.7**: GraphRAG 6层管道（意图识别→实体链接→Schema检索→Cypher生成→校验修复→答案合成）
- **v3.8**: L1结果缓存 + Schema双重过滤 + Few-shot注入 + 并行化 + 意图贯通（见第七节）

## 一、关系语义元数据存储

### 1.1 新增 SQLite 表：relation_semantics

```sql
CREATE TABLE relation_semantics (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    prefix        VARCHAR(10) NOT NULL,        -- 关联 systems.prefix
    rel_type      VARCHAR(200) NOT NULL,        -- 关系类型原名，如 "TREATS"
    display_name  VARCHAR(200) DEFAULT '',       -- 显示名，如 "治疗"
    description   TEXT DEFAULT '',               -- 语义描述
    source_hint   VARCHAR(200) DEFAULT '',       -- 典型源实体标签
    target_hint   VARCHAR(200) DEFAULT '',       -- 典型目标实体标签
    cardinality   VARCHAR(30) DEFAULT '',        -- 基数: one_to_one/one_to_many/many_to_many
    symmetry      VARCHAR(30) DEFAULT '',        -- 对称性: symmetric/asymmetric/reflexive
    transitivity  VARCHAR(30) DEFAULT '',        -- 传递性: transitive/intransitive/none
    created_at    VARCHAR(30) DEFAULT '',
    updated_at    VARCHAR(30) DEFAULT '',
    UNIQUE(prefix, rel_type)
);
```

### 1.2 选择 SQLite 而非 JSON 的理由

| 维度 | SQLite 新表 | JSON 文件 |
|------|------------|-----------|
| 按 prefix 查询 | `WHERE prefix='MED_'` 一条 SQL | 加载全文件遍历 |
| 按 rel_type 更新 | `UPDATE ... WHERE ...` | 读→改→写全文件 |
| 并发安全 | SQLite 自带事务 | 需手动加锁 |
| 前端对接 | 与现有 system API 一致 | 需新 API 读文件 |
| 数据一致性 | 通过 prefix 关联 systems 表 | 无关联 |

## 二、QueryService 重写

### 2.1 核心设计：语义驱动替代硬编码

```
v3.5 (硬编码):                    v3.6 (语义驱动):
─────────────                     ──────────────
_INTENT_PATTERNS = {              从 SQLite 读取语义:
  "disease_symptoms": {            ├── MED_TREATS: 治疗 (asymmetric)
    pattern: r"症状|symptom",      ├── MED_HAS_SIDE_EFFECT: 副作用 (asymmetric)
    cypher: "MATCH (d:Disease)     ├── EDU_TEACHES: 教授 (many_to_many, asymmetric)
    -[:HAS_SYMPTOM]->..."          └── EDU_ENROLLED: 选课 (many_to_many)
  },
  "drug_disease": {...},              ↓
  "drug_side_effect": {...},        注入 LLM Prompt
  ...                                ↓
}                                 动态规则引擎使用
```

### 2.2 LLM Prompt 增强

```
图谱说明：[系统描述]

关系语义：
| 关系类型 | 显示名 | 描述 | 基数 | 对称性 | 传递性 |
|----------|--------|------|------|--------|--------|
| MED_TREATS | 治疗 | 药物治疗疾病 | M:N | 非对称 | 非传递 |
| MED_HAS_SIDE_EFFECT | 副作用 | 药物产生副作用 | M:N | 非对称 | 非传递 |

Schema:
[动态 Schema 摘要]

用户问题: [question]
```

### 2.3 动态规则引擎

```python
def _ask_rules(question, prefix):

    1. 用模糊匹配找到问题中的实体名
    2. 查询该实体的所有关联（动态 Schema 遍历）
    3. 用语义中的 display_name 格式化结果
```

## 七、v3.8 GraphRAG 查询管道架构

**基于**: v3.7.1（6层管道：意图识别→实体链接→Schema检索→Cypher生成→校验修复→答案合成）  
**目标**: 在不改变主干流程的前提下，通过缓存分层、并行化、Few-shot 注入、意图贯通等 7 项优化，提升查询准确率与响应性能。

### 7.1 完整架构（v3.8）

```
用户问题
   │
   ├─ 0. L1 结果缓存检查                        【新增】
   │     输入: prefix + question
   │     Key: f"{prefix}:{question.strip().lower()}"
   │     命中 → 直接返回缓存 {answer, cypher, raw_data}（TTL 5min）
   │
   ├── LLM 已配置？───是──→ LLM 路径（6层管道）
   │                        │
   │                        ├─ 1. _extract_intent_and_entities  (LLM)
   │                        │     输入: 问题
   │                        │     输出: {intent, entities, question_type}
   │                        │     JSON解析: 代码块提取→直接解析→括号计数 三级兜底
   │                        │
   │                        ├─ 2. _link_entities                (Neo4j)
   │                        │     输入: entities
   │                        │     输出: ("肠道 → 匹配到: 肠道", linked_labels)
   │                        │     匹配: n.name CONTAINS $name
   │                        │
   │                        ├─ 3. Schema + 语义检索（并行）       【优化: ThreadPoolExecutor】
   │                        │     ├─ _get_schema_summary         (Neo4j, 缓存30min)
   │                        │     │   输入: prefix + linked_labels
   │                        │     │   双重过滤: 标签过滤 + 关系类型过滤   【优化】
   │                        │     │   输出: 过滤后的 Schema 文本
   │                        │     │
   │                        │     └─ _build_semantics_section   (SQLite, 缓存30min)
   │                        │         输入: prefix
   │                        │         输出: 语义 Markdown 表
   │                        │         语义修改后主动失效              【优化】
   │                        │
   │                        ├─ 4. _generate_cypher               (LLM)
   │                        │     输入: 问题 + intent + question_type + 实体
   │                        │           + Schema + 语义
   │                        │           + Few-shot 示例（1~2个）     【新增】
   │                        │     输出: Cypher 语句
   │                        │
   │                        ├─ 5. _validate_cypher + _repair_cypher (×2次重试)
   │                        │     输入: Cypher
   │                        │     安全检查: 拦截 CREATE/MERGE/DELETE/SET/REMOVE
   │                        │     语法校验: EXPLAIN 执行计划检查
   │                        │     失败修复: 错误信息回灌 LLM 修正
   │                        │     输出: (通过校验的 Cypher, failure_stage)   【优化: 细粒度错误】
   │                        │
   │                        └─ 6. _synthesize_answer             (Neo4j + LLM)
   │                              输入: 查询结果 JSON + intent      【优化: 意图感知】
   │                              裁剪前20行 → LLM 严格转述（禁止添加领域知识）
   │                              按 intent 调整回答风格（lookup列举/aggregate给数字）
   │                              输出: 自然语言回答
   │                              ↓
   │                        写入 L1 结果缓存                      【新增】
   │
   └── LLM 不可用或失败──→ 规则引擎路径（降级）
                            │
                            ├─ _find_node_by_question   (最长子串匹配)
                            ├─ MATCH 全向关系查询        (Neo4j)
                            └─ _format_rel_groups       (语义 display_name)
```

### 7.2 意图分类（与下游联动）

| 意图 | 触发词 | Cypher 特征 | 答案合成提示 |
|------|--------|-------------|-------------|
| lookup | "是什么""和什么有关" | MATCH 关联查询 | "列出所有关联关系" |
| aggregate | "多少""几个" | count/collect | "给出统计数字" |
| path | "什么关系""如何关联" | 路径查询 | "描述关联路径" |
| compare | "区别""不同" | 双实体对比 | "对比差异" |
| unknown | 其他 | 通用生成 | 通用提示 |

**意图贯通**: 第 1 层提取的 `intent` 同时流向第 4 层（Cypher 生成 prompt）和第 6 层（答案合成 prompt）。

### 7.3 三层缓存设计

| 层级 | 缓存 | Key | TTL | 失效策略 |
|------|------|-----|-----|----------|
| L1 | 查询结果缓存（新增） | `prefix:question` | 5 min | 时间过期 |
| L2 | Schema 缓存 | prefix | 30 min | 时间过期 + **导入后主动失效** |
| L3 | 语义缓存 | prefix | 30 min | 时间过期 + **语义修改后主动失效** |

**主动失效触发点**:

| 操作位置 | 动作 | 失效缓存 |
|----------|------|----------|
| `SystemService.upsert_relation_semantic` | 修改语义 | L3 语义缓存（该 prefix） |
| `SystemService.delete_relation_semantic` | 删除语义 | L3 语义缓存（该 prefix） |
| `ImportService` 导入完成 | 图谱数据变更 | L2 Schema 缓存 + L1 结果缓存（该 prefix） |

### 7.4 Schema 双重过滤

| 过滤维度 | v3.7.1 | v3.8 |
|----------|--------|------|
| 标签 | 只保留命中标签 | 只保留命中标签（不变） |
| 关系类型 | 全量保留 | **只保留命中标签之间实际存在的关系**（新增） |

关系类型过滤 Cypher:
```cypher
MATCH (a)-[r]->(b)
WHERE any(l IN labels(a) WHERE l IN $linked_labels)
  AND any(l IN labels(b) WHERE l IN $linked_labels)
RETURN DISTINCT type(r) AS rel_type
```

**效果**: 50 标签 / 100 关系的系统，问题只涉及 2 个标签时，关系类型从 100 降到 3~5 个。

### 7.5 Few-shot 示例注入

**存储**: `backend/data/fewshots.jsonl`，启动时加载到内存。

**示例格式**:
```json
{"question": "阿司匹林治疗什么疾病", "cypher": "MATCH (d:MED_Drug)-[r:MED_TREATS]->(dis:MED_Disease) WHERE d.name CONTAINS '阿司匹林' RETURN DISTINCT dis.name", "prefix": "MED_"}
```

**来源**:
- 预置示例（针对医疗系统手写 5~10 个典型案例）
- 成功案例回流（校验通过 + 结果非空的查询自动入库）

**注入位置**: `_generate_cypher` prompt 中的「参考示例」段落，每次注入 1~2 个最相关示例。

### 7.6 答案合成的准确性原则

**核心原则**: 严格忠实于数据，禁止添加任何图谱结果中没有的信息。

**反例约束**: 数据只有"急性胃肠炎→[影响]→肠道"，就只说"急性胃肠炎影响肠道"，不得添加"可能引起不适"等任何额外解释。

**LLM 失败降级**: `_format_cypher_result()` 模板化输出。

### 7.7 新增数据结构

```python
# L1 结果缓存（新增）
self._result_cache: dict[str, tuple[float, dict]]
# key: "MED_:肠道影响身体的什么部位"
# value: (timestamp, {"answer": ..., "cypher": ..., "raw_data": ...})

# 失败阶段枚举（新增）
failure_stage: str | None
# "intent_extraction" | "entity_linking" | "cypher_generation" | "validation" | "execution"
```

### 7.8 Prompt 大小控制

| 段落 | 控制策略 |
|------|----------|
| Schema | 双重过滤（标签 + 关系类型） |
| 语义 | 全量（通常较小） |
| Few-shot | 最多 2 个示例 |
| 实体链接 | 最多 5 个候选/实体 |
| 查询结果 | 最多 20 行，JSON 裁剪 3000 字符 |
| 答案合成 | 结果 JSON 裁剪 3000 字符 |

**监控**: 估算 token > 8000 时 `logger.warning`。

### 7.9 性能指标对比

| 指标 | v3.7.1 | v3.8 |
|------|--------|------|
| LLM 调用次数 | 3 次 | 3 次 |
| LLM 调用（修复） | 4~5 次 | 4~5 次 |
| 重复问题延迟 | 2~5s | ~10ms（L1 命中） |
| Schema+语义检索 | 串行 ~200ms | 并行 ~100ms |
| 语义修改生效 | 最多 30min | 立即 |
| 大 Schema prompt | 全量关系类型 | 只保留相关关系 |
| Cypher 准确率 | 纯 LLM 能力 | + Few-shot 示例引导 |

### 7.10 实施优先级

| 优先级 | 优化项 | 影响 | 改动量 |
|--------|--------|------|--------|
| P0 | 语义缓存主动失效 | 用户体验（修改立即生效） | 小 |
| P0 | Few-shot 示例注入 | 准确率（Cypher 生成精度） | 中 |
| P1 | Schema 关系类型过滤 | 性能（大 Schema 时 prompt 缩小） | 小 |
| P1 | L1 查询结果缓存 | 性能（重复问题秒回） | 小 |
| P2 | 答案合成意图感知 | 准确性（答案更贴合问题） | 小 |
| P2 | 并行化独立步骤 | 性能（减少 100~200ms） | 中 |
| P3 | 错误处理细粒度化 | 可观测性 | 小 |

### 7.11 已知限制与改进方向

| 限制 | 影响 | 改进方向 |
|------|------|----------|
| 缓存均在内存 | 重启丢失 | 可选：Redis 持久化 |
| 意图识别 5 类 | 复杂查询分类可能不准 | 增加类别或细粒度分类 |
| 实体链接仅 CONTAINS | 模糊匹配精度有限 | 可选：向量相似度匹配 |
| Few-shot 静态加载 | 新案例需重启 | 可选：热加载 / 向量检索示例 |
| 结果缓存无意图校验 | 相似问题可能误命中 | 缓存 Key 加入 intent |
| 无可观测性 Trace | 失败案例难追踪 | 可选：结构化日志 + 失败案例入库 |

## 二、Layer 1: Excel Sheet 自动检测与解析

### 2.1 现状问题

当前 `preview_excel` 硬编码了 `"实体"` 和 `"关系"` 作为 Sheet 名称，存在以下问题：
- 用户 Sheet 名可能是 "Entities"、"实体数据"、"节点"、"nodes" 等变体
- 大小写敏感问题
- 无法自动判断哪个 Sheet 是实体表、哪个是关系表

### 2.2 设计方案

新增 `ExcelSheetDetector` 类（`backend/services/excel_detector.py`），通过分析每个 Sheet 的表头来自动识别实体 Sheet 和关系 Sheet。

```
Sheet 识别规则:

1. 遍历所有 Sheet，跳过"使用说明"、"readme"、"模板说明"等引导 Sheet（以 ["使用", "说明", "readme", "帮助", "help", "guide"] 开头的 Sheet 名）

2. 对每个候选 Sheet：
   - 读取第 1 行作为表头
   - 实体 Sheet 识别：表头包含 "标签"(或 label/type/类型/entity_type) 和 "名称"(或 name/实体名称/node_name)
   - 关系 Sheet 识别：表头包含 "源实体"(或 source/src/from/start) 和 "关系类型"(或 type/relation/rel_type) 和 "目标实体"(或 target/to/end/dst)

3. 匹配算法：
   - 对表头做归一化处理（去空格、lower、去下划线）
   - 实体关键词: ["标签", "label", "type", "类型", "entity_type", "类别", "category"]
   - 名称关键词: ["名称", "name", "实体名称", "node_name", "实体", "entity"]
   - 源关键词:   ["源实体", "source", "src", "from", "start", "源", "source_name", "源名称"]
   - 关系关键词: ["关系类型", "type", "relation", "rel_type", "关系", "关系名", "relationship", "edge_type"]
   - 目标关键词: ["目标实体", "target", "to", "end", "dst", "目标", "target_name", "目标名称"]

4. 匹配打分：实体匹配分 = entity_label_score + entity_name_score
              关系匹配分 = rel_source_score + rel_type_score + rel_target_score
   - 选取得分最高且超过阈值的 Sheet 作为对应类型

5. 如果无法自动识别，返回候选列表让用户手动选择
```

**解析结果数据结构**：

```python
@dataclass
class ParsedSheet:
    sheet_name: str
    sheet_type: str          # "entity" | "relationship" | "unknown"
    headers: list[str]       # 原始表头
    columns: dict[str, int]  # 规范化列名 → 列索引
    rows: list[dict]         # 每行数据 (key=规范化列名)
    row_count: int

@dataclass  
class ExcelParseResult:
    entity_sheet: ParsedSheet | None
    relationship_sheet: ParsedSheet | None
    unmatched_sheets: list[str]     # 无法识别的 Sheet 名称
    parse_errors: list[str]         # 解析过程中的错误
```

### 2.3 属性列灵活处理

实体 Sheet 除了 `label` 和 `name` 两列外，其余列自动视为属性（key-value），在 Neo4j 中作为节点属性存储。

关系 Sheet 中如果存在第 4 列及以后的列，也视为关系的属性。

## 三、Layer 2: 数据验证器

### 3.1 现状问题

当前完全没有数据验证，所有解析结果直接写入 Neo4j。

### 3.2 设计方案

新增 `ImportValidator` 类（`backend/services/import_validator.py`），在解析完成后、写入 Neo4j 前进行多层验证。

#### 3.2.1 验证规则清单

**A. 格式验证**
- 实体 label/name 不为空
- 关系 source_name / type / target_name 不为空
- 属性值类型检查（确保是可存储的类型：string/number/boolean）

**B. 完整性检查**
- 必填列是否存在（每个解析出的行是否所有必填字段都有值）
- 检查缺失字段的具体行号

**C. 重复检查**
- 实体内重复：同一 label + name 组合在导入数据中不能出现多次
- 关系内重复：同一 source_name + type + target_name 组合不能重复

**D. 追加模式冲突检查**（仅 append 模式）
- 查 Neo4j：导入数据中的实体（label + name）是否已存在于目标系统中
  - 完全存在 → WARNING 级别提示
  - 部分字段不同但 name 相同 → ERROR 级别阻止（或提供覆盖选项）
- 查 Neo4j：导入数据中的关系是否已存在

#### 3.2.2 验证报告数据结构

```python
class ValidationSeverity(str, Enum):
    ERROR = "error"       # 必须修复才能继续
    WARNING = "warning"   # 可忽略但需注意

    field: str | None            # 涉及的字段名
    detail: dict | None          # 额外详情

@dataclass  
class ValidationReport:
    is_valid: bool               # ERROR=0 时为 True
    entity_count: int
    relationship_count: int
    issues: list[ValidationIssue]
    
    # 快捷统计
    @property
    def error_count(self) -> int: ...
    @property
    def warning_count(self) -> int: ...
    
    # 追加模式专用
    conflict_entities: list[dict]   # [{label, name, existing_props}]
    conflict_relationships: list[dict]
```


## 四、Layer 3: Cypher 生成中间层

### 4.1 设计动机

当前代码直接将原始数据传入 `batch_create_nodes` / `batch_create_relationships`，在其中混合了前缀添加、属性整理和 Cypher 生成逻辑。

引入中间层的好处：
- **关注点分离**：数据转换（加前缀）与 Neo4j 操作（执行 Cypher）解耦
- **可预览**：在真正写入前，用户可以看到即将执行的 Cypher 语句
- **可调试**：Cypher 生成的每一步都是可追踪的
- **可复用**：无论是新建还是追加，转换逻辑完全相同

### 4.2 设计方案

新增 `CypherGenerator` 类（`backend/services/cypher_generator.py`）。

```python
@dataclass
class CypherStatement:
    """单条 Cypher 语句及其参数"""
    statement: str
    params: dict
    description: str         # 人类可读描述，如 "CREATE (:MED_Disease {name: '高血压'})"

@dataclass
class CypherBatch:
    """一批 Cypher 语句"""
    entity_statements: list[CypherStatement]
    relationship_statements: list[CypherStatement]
    entity_count: int
    relationship_count: int
    
    def all_statements(self) -> list[CypherStatement]:
        return self.entity_statements + self.relationship_statements
```

#### 4.2.1 实体 Cypher 生成

```python
def generate_entity_cypher(
    entities: list[dict], 
    prefix: str,
    strategy: str = "MERGE"  # "CREATE" | "MERGE"
) -> list[CypherStatement]:
```

**策略说明**：
- `CREATE`：新建模式，直接创建，速度快（假设全新图谱无冲突）
- `MERGE`：追加模式，匹配已有或新建，防止重复

**生成示例**：

```cypher
# 新建模式: CREATE
UNWIND $batch AS row
CREATE (n:`MED_Disease` {name: row.name, icd_code: row.icd_code})
RETURN count(n) AS created

# 追加模式: MERGE (避免重复创建同名节点)
UNWIND $batch AS row
MERGE (n:`MED_Disease` {name: row.name})
ON CREATE SET n += row.props
RETURN count(n) AS created
```

参数绑定：
```python
{
    "batch": [
        {
            "name": "高血压",
            "props": {"name": "高血压", "icd_code": "I10", "description": "..."}
        },
        ...
    ]
}
```

#### 4.2.2 关系 Cypher 生成

**当前重大 Bug**：
```python
# 当前代码 (neo4j_repository.py L649)
f"CREATE (src)-[r:`{prefix}`]->(tgt) "  # ← 静态写死 prefix，所有关系类型相同！
```
这会导致所有关系被创建为 `MED_` 类型，而非 `MED_包含`、`MED_导致` 等。

**修复方案**：动态关系类型必须使用 APOC 或字符串拼接方式：

```python
# 方案 A: 使用 APOC (推荐)
"CALL apoc.create.relationship(src, row.full_type, {}, tgt) YIELD rel "

# 方案 B: 分批按类型执行 (无 APOC 依赖)
# 按 full_type 分组，每组一条 MERGE/CREATE 语句
```

推荐方案 A，因为当前 `batch_create_nodes` 已经使用了 APOC，Neo4j 环境具备 APOC 插件。

**生成示例**：

```cypher
UNWIND $batch AS row
MATCH (src {name: row.source_name})
MATCH (tgt {name: row.target_name})
CALL apoc.create.relationship(src, row.full_type, row.props, tgt) YIELD rel
RETURN count(rel) AS created
```

#### 4.2.3 前缀处理

前缀统一在 `CypherGenerator` 中处理，调用方不需要关心：

```python
class CypherGenerator:
    def __init__(self, prefix: str):
        self.prefix = prefix
    
    def _full_label(self, short_label: str) -> str:
        """将短标签转为带前缀的完整标签"""
        return f"{self.prefix}{short_label}"
    
    def _full_rel_type(self, short_type: str) -> str:
        """将短关系类型转为带前缀的完整关系类型"""
        return f"{self.prefix}{short_type}"
```

### 4.3 额外节点属性处理

`batch_create_nodes` 当前只提取 `name` 作为属性：
```python
"props": {"name": n["name"], **(n.get("properties", {}))},
```
但 `preview_excel` 中从 Excel 读取的属性是直接平铺在 entity dict 中的（如 `{label: "疾病", name: "高血压", icd_code: "I10"}`），不是放在 `properties` 字段中。

**修复**：在 CypherGenerator 中自动区分固定字段（label, name）和自定义属性：

```python
# 固定字段: label, name (不放入 props)
# 其余字段: 放入 props

def _extract_props(self, entity: dict) -> dict:
    skip_keys = {"label", "name", "properties"}
    extra = {k: v for k, v in entity.items() if k not in skip_keys}
    return {"name": entity["name"], **extra}
```

## 五、Layer 4: Neo4j 事务管理器（备份与回滚）

### 5.1 设计动机

当前没有任何备份回滚机制。如果在导入过程中出错（部分实体已写入但关系写入失败），数据会处于不一致状态。

### 5.2 设计方案

新增 `Neo4jTransactionManager` 类（`backend/services/neo4j_tx_manager.py`）。

#### 5.2.1 备份策略

由于 Neo4j Community 不支持完整的数据库级备份/快照，采用**元数据快照 + 按 Prefix 范围的备份**策略：

```python
@dataclass
class BackupSnapshot:
    """备份快照"""
    snapshot_id: str          # 时间戳生成的唯一 ID
    prefix: str
    created_at: str           # ISO 8601
    node_count: int           # 快照时节点数
    relationship_count: int   # 快照时关系数
    
    # 备份关键数据：导出该 prefix 下所有节点和关系的 JSON 表示
    nodes_backup: list[dict]  # [{elementId, labels, properties}]
    relationships_backup: list[dict]  # [{elementId, type, startNode, endNode, properties}]
```

#### 5.2.2 备份流程

```python
class Neo4jTransactionManager:
    def create_backup(self, prefix: str) -> BackupSnapshot:
        """
        1. 统计 prefix 下的节点数和关系数
        2. 导出该 prefix 下的所有节点数据（elementId, labels, properties）
        3. 导出该 prefix 下的所有关系数据
        4. 将 snapshot 存储到文件系统 (backend/data/backups/{snapshot_id}.json)
        5. 返回 BackupSnapshot 对象
        """
    
    def execute_batch(self, cypher_batch: CypherBatch, prefix: str) -> dict:
        """
        1. 先创建备份 create_backup(prefix)
        2. 在 Neo4j 事务中执行所有 Cypher 语句
        3. 验证结果（计数是否匹配）
        4. 返回执行结果 {entities_created, relationships_created}
        如果执行失败，抛出异常，备份文件保留供手动恢复使用
        """
    
    def restore_from_backup(self, snapshot_id: str) -> bool:
        """
        回滚操作:
        1. 读取 snapshot 文件
        2. 删除当前 prefix 下所有数据
        3. 从备份数据重建节点和关系
        4. 返回是否成功
        """
```

```
├── 20260726_150510_CAR_.json
```

## 八、现有 Bug 修复计划

### 8.1 batch_create_relationships Cypher Bug

**问题**：关系类型静态写死为 prefix，无法区分不同关系。

**修复**：使用 APOC 按行动态创建关系类型：
```python
def batch_create_relationships(self, rels: list[dict], prefix: str) -> int:
    if not rels:
        return 0
    result = self._run_write(
        "UNWIND $rels AS row "
        "MATCH (src {name: row.source_name}) "
        "MATCH (tgt {name: row.target_name}) "
        "CALL apoc.create.relationship(src, row.full_type, {}, tgt) YIELD rel "
        "RETURN count(rel) AS created",
        {"rels": [
            {
                "full_type": f"{prefix}{r['type']}",
                "source_name": r["source_name"],
                "target_name": r["target_name"],
            }
            for r in rels
        ]},
    )
    return result[0]["created"] if result else 0
```

### 8.2 batch_create_relationships 缺少 prefix 参数

**问题**：`import_service.py` 第 100 行和第 142 行调用 `batch_create_relationships` 时缺少 `prefix` 参数。

**修复**：
```python
# 第 100 行
rel_count = self.repo.batch_create_relationships(preview.relationships, prefix)

# 第 142 行  
rel_count = self.repo.batch_create_relationships(preview.relationships, prefix)
```

### 8.3 节点额外属性丢失

**问题**：`preview_excel` 将 Excel 中除 label/name 外的其他列平铺在 entity dict 中，但 `batch_create_nodes` 只从 `n.get("properties", {})` 中读取额外属性，导致属性丢失。

**修复**：在 CypherGenerator 中自动提取额外属性（见 4.2.3）。

## 十、关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 关系动态类型方案 | APOC | 当前已依赖 APOC 创建节点，保持一致 |
| 备份粒度 | 按 Prefix 全量导出 | 简单可靠，适合中小规模图谱 |
| 备份存储 | JSON 文件 | 可读、可手动恢复、无额外依赖 |
| 冲突处理 | 用户可选择策略 | 不同场景有不同需求（医学→严格，汽车→宽松） |
| 验证阶段 | 两步验证 | 先本地验证（快），再 Neo4j 验证（追加模式） |
| Cypher 生成 | 独立中间层 | 可预览、可调试、可测试 |

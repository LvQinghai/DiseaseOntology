# DiseaseOntology v4.5 设计文档

> 版本：v4.5  
> 日期：2026-07-30  
> 前置版本：v4.0（多系统隔离、关系编辑、图谱竞态防护）  
> 本版本状态：核心闭环已实现，已完成代码级验收，进入真实关系数据库联调阶段

> 实现说明：本次版本将关系数据库导入的“连接—映射—预览—验证—确认—执行—结果—回滚”流程落地为分层、可校验、可补偿的同步导入闭环。当前接口仍以兼容 `/db/*` 接口为主，阶段状态在请求完成后一次性返回；实时进度轮询、SSE/WebSocket、流式大数据导入和导入会话 API 属于后续增强范围。

---

## 一、版本目标

v4.5 在现有“导入新数据”功能中，补充已经提供入口但尚未实现的**关系型数据库导入知识图谱**能力。用户选择“从关系数据库导入”后，进入“连接—发现—映射—验证—确认—执行—结果—防重复”的完整导入闭环；现有 Excel 导入入口和流程不在本版本中重复设计。

本版本的核心原则：

1. Excel 与关系数据库共享同一套标准化实体/关系数据结构、验证规则、导入计划和 Neo4j 写入机制。
2. 数据库连接只用于读取，不修改源数据库；默认采用只读账号、最小权限和查询超时。
3. 关系数据库通过表名约定识别数据来源：`Ontology` 表提供实体，`Relationship` 表提供关系。
4. 任何缺少的必需表、必需字段、实体引用或系统隔离条件，都必须在执行前明确提示。
5. 导入成功后记录来源指纹，阻止用户无意重复导入；用户明确选择“强制重新导入”时才允许继续。
6. v4.5 优先完成同步可用的稳定闭环，接口和会话模型为后续异步大文件导入预留扩展点。

## 二、v4.5 版本实现总结

### 2.1 版本定位

v4.5 的实际交付重点是补齐关系型数据库到知识图谱的同步导入闭环，并解决导入确认阶段的参数解析、失败补偿、数据隔离和图谱展示问题。当前版本不是一次性完成所有规划能力，而是先交付“稳定可用、失败可恢复、结果可解释”的第一阶段实现。

### 2.2 已实现能力

| 能力 | 实现结果 |
|---|---|
| 数据库连接 | 基于 SQLAlchemy 连接 SQLite、MySQL、PostgreSQL 等数据库，并执行连接测试、表和字段读取 |
| 表与字段映射 | 支持用户选择实体表、关系表；自动推断实体名称、Label、关系源、关系目标和关系类型字段 |
| Label 标准化 | `TableMapping` 增加 `label_column`；业务标签统一映射到 `entity["label"]`，Label 字段不再作为普通属性保存 |
| 数据预览 | 返回标准化实体和关系数据，支持前端确认字段映射及预览结果 |
| 五阶段导入 | 按 `mapping`、`reading`、`cypher`、`execution`、`result` 划分执行阶段，并返回阶段状态、错误和警告 |
| Cypher 转换 | 使用统一 `CypherGenerator` 生成实体和关系批次，实体 Label 生成真实 Neo4j Label |
| Neo4j 执行 | 通过事务管理器创建快照、批量写入节点和关系，并统计实际创建数量 |
| 失败补偿 | Neo4j 写入失败时恢复导入前快照；新建系统失败时清理本次创建的 SQLite 临时系统记录 |
| 结果校验 | 对实际实体、关系写入结果进行校验；计数偏差降级为 warning，不因统计偏差误判整个导入流程 |
| 前端错误处理 | 修复确认导入时对象直接拼接导致的 `[object Object]`，并修复 FastAPI JSON body 参数被误解析为 query 参数的问题 |
| 系统管理 | 系统下拉框按 SQLite 自增 ID 升序展示；前缀通过 `normalize_prefix()` 统一标准化 |
| 图谱展示 | 后端按 Neo4j Label 动态分配节点颜色，前端按实际节点类型生成图例和颜色，避免新导入系统全部回退为单一绿色 |

### 2.3 已验证的关键边界

1. **Label 字段不能降级为普通属性**：没有有效业务 Label 时，预览阶段直接报错，要求通过 `label_column` 或 `target_label` 明确指定。
2. **导入失败不能遗留脏数据**：Neo4j 快照恢复与 SQLite 临时系统记录清理形成失败补偿边界。
3. **统计必须基于实际批次**：实体和关系数量以实际生成、执行的 batch 行数为准，不直接使用源表总行数。
4. **系统数据必须隔离**：实体、关系、图谱查询和节点颜色均基于目标系统 prefix/Label 处理。
5. **SQLite 文件完整性**：系统元数据库通过 SQLite 驱动和完整性检查验证，导入失败补偿不以破坏 SQLite 文件为代价。

### 2.4 当前交付边界

已经完成的是同步导入闭环和核心可靠性修复；以下能力仍属于后续版本或增强范围：

- 新版导入 Session API 及独立会话持久化；
- `source_fingerprint` 指纹、防重复导入和完整导入审计；
- 后台任务、实时进度轮询、SSE/WebSocket；
- 流式读取和超大数据量导入；
- 完整的 SQL Server、Oracle、SSL/云数据库方言适配；
- 前端独立的 Label 字段选择控件和完整 ImportWizard 组件拆分。

### 2.5 端到端验收重点

真实关系数据库联调时，应重点确认：

```text
数据库业务标签字段
  → preview_db()
  → entities[].label
  → CypherGenerator
  → Neo4j 节点 Label
  → 左侧本体树分组 / 右侧图谱颜色
```

建议使用以下查询核验目标前缀下的实际 Label：

```cypher
MATCH (n)
WHERE any(label IN labels(n) WHERE label STARTS WITH '目标前缀_')
RETURN labels(n), count(*)
ORDER BY count(*) DESC
```

## 三、现状与复用范围

当前项目已经具备 Excel 导入的主要能力：

- `backend/services/excel_detector.py`：Sheet 类型检测、表头归一化、实体/关系标准字段映射。
- `backend/services/import_validator.py`：必填项、重复、关系引用完整性和追加模式冲突验证。
- `backend/services/cypher_generator.py`：生成实体与关系批量 Cypher。
- `backend/services/neo4j_tx_manager.py`：备份、批量写入、执行结果统计和回滚。
- `backend/services/import_service.py`：已有 SQLAlchemy 数据库连接、表结构读取、预览和导入雏形。
- `backend/routers/import_router.py`：已有 `/api/import/db/test`、`/db/tables`、`/db/preview`、`/db/import`、`/db/append` 兼容接口。
- 前端 `App.vue`、`frontend/src/api/index.ts`、`frontend/src/types/index.ts` 和 Pinia Store 已承载 Excel 导入向导的部分状态。

现有数据库实现可以作为连接层原型，但不能直接视为 v4.5 最终方案，主要原因是：

- 当前数据库映射需要用户提交 `entity_mappings`，尚未按 `Ontology`/`Relationship` 约定自动发现。
- `_read_table()` 使用字符串拼接表名，存在标识符注入和跨数据库分页语法不一致风险。
- 数据库预览、验证、导入尚未与新版 Excel 的验证、备份、Cypher 预览和会话状态完全统一。
- `test_connection()` 对所有数据库直接使用 `connect_timeout`，不同驱动的参数兼容性需要方言适配。
- 数据库密码不应在导入会话、日志或前端持久化中明文保存。

因此 v4.5 采用“复用领域层，重构数据源适配层”的方案。

## 四、用户功能设计

### 4.1 已有入口与本版本范围

当前“导入新数据”功能已经提供“从 Excel 导入”和“从关系数据库导入”两个选项。Excel 选项已有实现，不属于本版本的新增范围。

本版本仅实现用户选择“从关系数据库导入”后的数据库导入流程，并复用 Excel 已验证的实体/关系分析、数据验证、导入确认、Neo4j 写入、结果展示和防重复设计。两个入口在后续领域处理层汇合，但不新增或调整入口 UI。

### 4.2 数据库导入向导

```text
1. 进入已有的“从关系数据库导入”选项
2. 选择导入模式

   ├─ 新建知识图谱系统
   └─ 追加到已有系统
3. 填写数据库连接信息
4. 测试连接
5. 发现数据库表和字段
6. 自动检查 Ontology / Relationship
7. 展示表结构与数据预览
8. 字段分析与映射确认
9. 执行完整数据验证
10. 展示错误、警告、冲突和统计
11. 用户确认导入计划与冲突策略
12. 创建备份并执行导入
13. 展示导入结果、快照和回滚入口
14. 刷新系统、图谱、关系类型和统计
```

#### 3.2.1 确认执行阶段的分层控制

用户确认导入后，后端按以下阶段顺序执行，并为每个阶段返回 `key`、`label`、`status` 和可选的 `message`：

| 阶段 | 责任 | 成功条件 |
|---|---|---|
| `mapping` | 校验实体表、关系表及字段映射 | 必需表存在，必填字段可解析 |
| `reading` | 读取并标准化关系数据库数据 | 数据可读取并转换为实体/关系标准行 |
| `cypher` | 将标准行转换为 `CypherBatch` | 生成的实体、关系批次结构完整 |
| `execution` | 创建快照并执行 Neo4j 批量写入 | Neo4j 执行成功 |
| `result` | 校验实际节点、关系数量并更新统计 | 执行结果与目标系统统计一致 |

阶段状态使用 `pending`、`processing`、`success`、`error`。当前同步接口在请求结束时返回完整阶段列表，用于前端展示执行链路；阶段信息不是实时任务进度，后续异步化时沿用同一数据结构。

发生异常时，流程立即停止后续阶段，并执行补偿：Neo4j 若已创建快照则恢复快照；新建模式删除本次请求创建的 SQLite 系统临时记录；不得继续更新系统统计、初始化关系语义或刷新系统缓存。补偿结果写入 `warnings`、`errors` 和 `message`，便于用户判断是否需要人工处理。

### 4.3 必需表识别

数据库导入默认要求：

| 逻辑用途 | 默认表名 | 说明 |
|---|---|---|
| 实体来源 | `Ontology` | 每行至少包含实体标签和实体名称 |
| 关系来源 | `Relationship` | 每行至少包含源实体、关系类型、目标实体 |

表名匹配规则：

1. 默认不区分大小写，支持数据库方言的 schema，例如 `public.Ontology`。
2. 不做模糊匹配，避免把 `OntologyHistory` 误判为正式表。
3. 可在连接成功后显示实际发现的表名；若数据库大小写敏感，按数据库元数据返回结果匹配。
4. v4.5 第一阶段允许用户在高级设置中手动指定实际表名，但必须明确标记为 `Ontology` 和 `Relationship` 两种逻辑来源。
5. 两张表任意一张缺失时，禁止进入执行阶段，并提示具体缺失项，例如：`未找到实体来源表 Ontology`。

### 4.4 字段分析与标准字段

`Ontology` 标准字段：

| 标准字段 | 必填 | 推荐候选列名 |
|---|---:|---|
| `label` | 是 | `label`, `type`, `entity_type`, `节点类型`, `实体类型` |
| `name` | 是 | `name`, `entity_name`, `node_name`, `名称`, `实体名称` |
| `external_id` | 否 | `id`, `external_id`, `entity_id`, `实体ID` |
| 其他属性 | 否 | 原字段名保留为属性 |

`Relationship` 标准字段：

| 标准字段 | 必填 | 推荐候选列名 |
|---|---:|---|
| `source_name` | 是 | `source`, `source_name`, `src`, `from`, `源实体` |
| `type` | 是 | `type`, `relation`, `rel_type`, `relationship`, `关系类型` |
| `target_name` | 是 | `target`, `target_name`, `dst`, `to`, `目标实体` |
| `source_id` / `target_id` | 否 | `source_id`, `target_id`, `src_id`, `dst_id` |

字段分析采用与 `ExcelSheetDetector` 一致的“精确匹配优先、归一化后兜底匹配”规则。若存在多个候选列，前端必须要求用户确认，不能静默选择。无法推断必填字段时显示缺失字段、候选字段和示例值。

### 4.5 验证与确认

数据库数据进入统一 `ParsedSheet`/标准行结构后，复用 Excel 验证规则：

- 必需表和必需字段检查；
- 空值、类型转换和超长字符串检查；
- 实体名称、外部 ID 和关系唯一性检查；
- 关系源实体和目标实体存在性检查；
- 关系类型和标签合法性检查；
- 追加模式下的系统内冲突检查；
- 当前系统 prefix 隔离检查；
- 数据量、重复量、预计创建/更新/跳过数量统计。

验证结果分为 `error`、`warning`、`info`：

- 存在 `error`：不可执行；
- 仅有 `warning`：允许用户确认后执行；
- `info`：用于展示数据来源、行数和字段映射信息。

执行前显示导入计划，至少包括实体和关系的创建、更新、跳过、冲突、失败预估，以及源数据库、表名、查询时间和数据指纹。

### 4.6 防止重复导入

每次数据库导入生成 `source_fingerprint`，建议由以下内容计算 SHA-256：

```text
数据库类型 + 服务器标识 + 数据库名 + schema +
Ontology/Relationship 表名 + 字段映射 + 查询条件 +
实体/关系数据内容摘要
```

安全要求：

- 不保存数据库密码；服务器标识可脱敏或使用用户配置的逻辑名称。
- 指纹、导入模式、目标系统、映射和结果写入导入审计记录。
- 同一系统、同一来源指纹和同一映射再次导入时，默认阻止并提示上次导入时间与结果。
- 用户选择“强制重新导入”并确认后才允许继续；强制导入仍保留审计记录。
- Excel 也应逐步接入相同的文件哈希/来源指纹机制，以统一防重复行为。

## 五、关系数据库连接设计

### 5.1 Python 通用接口

采用 SQLAlchemy 2.x 作为统一连接抽象，应用层不直接依赖某个数据库驱动：

```text
DatabaseConnectionProfile
  ├─ dialect / db_type
  ├─ host / port
  ├─ database
  ├─ schema
  ├─ username
  ├─ secret（仅服务端短生命周期使用）
  ├─ ssl_options
  ├─ connect_timeout
  └─ readonly

DatabaseAdapter
  ├─ validate_profile()
  ├─ test_connection()
  ├─ list_tables()
  ├─ get_columns(table)
  ├─ read_preview(table, limit)
  ├─ stream_rows(table, batch_size)
  └─ close()
```

连接池只在导入会话生命周期内创建，使用 `pool_pre_ping`、连接超时、查询超时和 `engine.dispose()`。所有表名、schema 名称先通过 SQLAlchemy Inspector 元数据校验，再使用方言安全的标识符处理，禁止直接拼接用户输入到 SQL。

### 5.2 支持的数据库

第一阶段通过 SQLAlchemy dialect + 官方/主流 DBAPI 驱动支持：

| 数据库 | SQLAlchemy dialect | 建议驱动 | v4.5 阶段 |
|---|---|---|---|
| SQLite | `sqlite` | 内置 `sqlite3` | 必须 |
| MySQL / MariaDB | `mysql+pymysql` | `PyMySQL` | 必须 |
| PostgreSQL | `postgresql+psycopg` | `psycopg` | 必须 |
| SQL Server | `mssql+pyodbc` | `pyodbc` + ODBC Driver | 推荐 |
| Oracle | `oracle+oracledb` | `oracledb` | 推荐 |

后续可通过同一接口增加：

- CockroachDB、TiDB 等兼容 PostgreSQL/MySQL 的数据库；
- IBM Db2、Firebird、SAP HANA 等 SQLAlchemy dialect；
- 云数据库，只要网络、驱动和认证方式满足部署环境要求。

不建议在第一阶段自行实现每种数据库的连接协议。SQLAlchemy 负责连接、事务、Inspector 和参数化 SQL；`DatabaseAdapter` 负责方言差异、分页、超时、schema 和流式读取。

### 5.3 连接安全

- 前端只提交连接表单到后端，不将密码写入 localStorage、Pinia 持久化或审计日志。
- 数据库账号遵循只读最小权限，仅允许读取指定 schema 的元数据和两张业务表。
- 禁止从数据库返回结果中执行任何 SQL、Cypher 或脚本内容。
- 主机、端口、schema、表名进行长度和字符集校验；禁止任意文件路径和任意 URL 协议。
- 生产部署建议增加出站网络白名单、TLS/SSL 校验、凭据保管服务和连接审计。
- 数据库连接错误向用户返回可操作的摘要，详细异常仅写服务端日志并脱敏。

## 六、后端架构设计

### 6.1 分层架构

```text
Import Router
    ↓
Import Session Service / Import Orchestrator
    ↓
Source Adapter
  ├─ ExcelSourceAdapter
  └─ RelationalDatabaseAdapter
    ↓
Normalized Dataset
  ├─ Ontology rows → entity ParsedSheet
  └─ Relationship rows → relationship ParsedSheet
    ↓
ImportValidator → ImportPlanService
    ↓
CypherGenerator → Neo4jTransactionManager
    ↓
SystemService + Audit/Idempotency Repository
```

数据库适配器只负责“连接、发现、读取、标准化”，不负责 Neo4j 写入；验证器、计划生成器和事务管理器也不应感知 MySQL/PostgreSQL 的具体连接细节。

### 6.2 建议模块

```text
backend/
├── models/
│   ├── import_task.py                 # 兼容旧模型
│   ├── import_session.py              # 导入会话、来源和状态
│   ├── database_connection.py         # 连接配置（密码不回传）
│   └── import_plan.py                 # 验证报告和导入计划
├── services/
│   ├── import_orchestrator.py         # 统一编排 Excel/数据库
│   ├── import_session_service.py      # 会话状态、指纹和审计
│   ├── database_adapter.py            # 通用适配器接口
│   ├── sqlalchemy_database_adapter.py# SQLAlchemy 实现
│   ├── database_schema_detector.py    # Ontology/Relationship 发现
│   ├── import_validator.py             # 统一验证
│   ├── cypher_generator.py             # 统一生成
│   └── neo4j_tx_manager.py            # 备份、执行、回滚
├── repositories/
│   └── import_audit_repository.py     # 重复检测与审计
└── routers/
    └── import_router.py               # 新会话接口，保留旧接口兼容
```

### 6.3 会话状态

```text
created → connected → discovered → mapped → validated
       → awaiting_confirmation → executing → completed
                                      └──────→ failed / rolled_back / cancelled
```

每个会话保存：来源类型、目标系统、表名、字段映射、验证摘要、数据指纹、冲突策略、快照 ID、执行统计和错误信息。连接凭据只存在于短生命周期内存或安全凭据引用中，不写入会话 JSON。

### 6.4 统一数据模型

数据库和 Excel 最终都转换成：

```text
ParsedSheet(
  sheet_name="Ontology" | "Relationship",
  sheet_type="entity" | "relationship",
  headers=[...],
  column_map={...},
  rows=[...],
  row_count=n,
)
```

建议后续将 `sheet_name` 泛化为 `source_name`，但 v4.5 可先保持兼容，在数据库分支中将逻辑表名映射为 `Ontology` 和 `Relationship`。

## 八、事务、回滚与幂等

### 8.1 执行顺序

```text
验证通过
  → 检查重复指纹
  → 创建 Neo4j prefix 快照
  → 批量写入实体
  → 批量写入关系
  → 更新 SQLite 系统统计
  → 初始化关系语义
  → 失效查询缓存
  → 写入审计结果
```

任何写入失败都应进入失败状态，并提供回滚。SQLite 系统记录、关系语义和导入审计应与 Neo4j 快照关联，不能只回滚图数据而遗留错误统计。

### 8.2 系统隔离

- 新建模式使用 `normalize_prefix()` 生成并校验 prefix。
- 追加模式只能使用目标系统已有 prefix。
- 实体、关系查询和冲突检查必须限制在目标 prefix 内。
- 关系节点匹配优先使用 `external_id`；没有稳定 ID 时至少同时限制名称和目标系统 prefix，防止同名实体跨系统匹配。

### 8.3 冲突策略

统一支持：

- `fail`：发现冲突直接终止；
- `skip`：跳过已存在记录；
- `merge`：合并非空属性；
- `overwrite`：以本次数据覆盖属性。

实体和关系建议分别保存策略，例如 `entity_strategy=merge`、`relationship_strategy=skip`，并在执行前展示给用户。

## 十、测试与验收标准

### 10.1 连接层

- SQLite、MySQL、PostgreSQL 成功连接和失败连接均有清晰反馈；
- 超时、认证失败、不可达、schema 不存在可区分提示；
- 连接关闭后无连接泄漏；
- 密码不出现在日志、返回值和持久化数据中。

### 10.2 表发现与字段映射

- 正确识别大小写不同的 `Ontology`、`Relationship`；
- 缺失实体表或关系表时准确提示缺失名称；
- 同名模糊表不会被误识别；
- 中英文、下划线和大小写变体能正确识别标准字段；
- 多候选字段要求用户确认。

### 10.3 数据验证与导入

- 空实体、重复实体、悬空关系、重复关系、错误类型均在执行前发现；
- 新建和追加模式均遵守 prefix 隔离；
- 实体和关系数量与实际批次写入数量一致；
- 导入结果包含 `mapping`、`reading`、`cypher`、`execution`、`result` 五个阶段及状态；
- 阶段异常会停止后续执行，并返回可读的错误信息；
- Neo4j 执行失败可按 snapshot 回滚；
- 新建模式失败时不会遗留本次创建的 SQLite 系统记录；
- Neo4j、SQLite、关系语义和审计记录状态一致；
- 重复指纹默认阻止，强制导入需要明确确认。

### 10.4 用户体验

- Excel 和数据库均经过同一套验证、确认、结果展示流程；
- 数据库未找到必需表时不会进入不可解释的空预览；
- 确认导入后前端展示五阶段执行结果、当前阶段状态、错误和警告；
- 导入结果明确显示实体、关系、跳过、失败、警告和回滚入口；
- 当前同步接口返回完成后的阶段结果，后续异步实时进度单独建设。

## 十二、设计结论

v4.5 不应把关系数据库导入实现为一组独立的“连接、预览、导入”接口，而应把它纳入统一导入会话。最重要的架构边界是：

```text
数据库适配器负责读取
标准化层负责转换
验证层负责判断
计划层负责解释
Neo4j 事务层负责写入与回滚
审计层负责幂等与追踪
```

这样既能支持 `Ontology`/`Relationship` 表约定，又能复用 Excel 导入已有能力，避免两套验证规则和两套执行结果长期分叉。v4.5 第一阶段以稳定、可审计、可回滚为优先，不在连接层保存敏感凭据，并为后续异步、流式和更多数据库方言保留扩展接口。
